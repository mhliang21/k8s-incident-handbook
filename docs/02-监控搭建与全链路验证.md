# K8s 故障排查 SOP · 第二篇：监控搭建与全链路验证

> 环境：kind v0.27 + kubectl v1.32 + Helm 3 · 3 节点集群
> 本篇记录 Prometheus 监控体系的完整搭建过程、5 条核心告警规则，以及如何用「制造故障」验证告警全链路。

## 一、架构总览

```
kube-prometheus-stack（Helm Chart）
├── Prometheus Operator     # 管理 Prometheus / Alertmanager / 告警规则 CRD
├── Prometheus              # 指标采集 + 告警评估
├── Alertmanager            # 告警去重、分组、路由、通知
├── Grafana                 # 可视化大盘
├── kube-state-metrics      # 采集集群资源对象状态（Pod/Node/Deployment）
└── node-exporter           # 采集节点 CPU/内存/磁盘等系统指标
```

数据流：`node-exporter / kube-state-metrics 采集 → Prometheus 存储评估 → Alertmanager 路由 → 通知渠道`

## 二、安装 kube-prometheus-stack

### 1. 精简配置 values.yaml（16GB 内存友好）

```yaml
alertmanager:
  alertmanagerSpec:
    replicas: 1
    resources:
      requests:
        memory: "100Mi"
      limits:
        memory: "200Mi"

prometheus:
  prometheusSpec:
    replicas: 1
    retention: 2d
    resources:
      requests:
        memory: "300Mi"
      limits:
        memory: "600Mi"

grafana:
  adminPassword: admin
  resources:
    requests:
      memory: "100Mi"
    limits:
      memory: "200Mi"

kube-state-metrics:
  resources:
    requests:
      memory: "50Mi"

prometheus-node-exporter:
  resources:
    requests:
      memory: "50Mi"
```

> ⚠️ 踩坑：`resources.requests` 和 `resources.limits` 必须**平级**，不能把 `limits` 缩进到 `requests` 下面，否则 Helm 报错 `expected any scalar, got &{map[memory:200Mi]}`。

### 2. 安装命令

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install kube-prometheus prometheus-community/kube-prometheus-stack \
  -f values.yaml \
  --namespace monitoring \
  --create-namespace

kubectl get pods -n monitoring -w   # 等全部 Running
```

> ⚠️ 踩坑：Helm 会**截断**过长的 Service 名，实际 Service 名不是 `kube-prometheus-prometheus` 而是 `kube-prometheus-kube-prome-prometheus`。用 `kubectl get svc -n monitoring` 确认实际名称。

### 3. 验证组件

```bash
kubectl get pods -n monitoring
# alertmanager-kube-prometheus-alertmanager-0
# kube-prometheus-grafana-xxx
# kube-prometheus-kube-state-metrics-xxx
# kube-prometheus-operator-xxx
# kube-prometheus-prometheus-node-exporter-xxx
# prometheus-kube-prometheus-prometheus-0
```

## 三、访问 Grafana 和 Prometheus

```bash
# Grafana（默认 admin/admin）
kubectl port-forward -n monitoring svc/kube-prometheus-grafana 3000:80
# 浏览器 http://localhost:3000

# Prometheus 告警页面
kubectl port-forward -n monitoring svc/kube-prometheus-kube-prome-prometheus 9090:9090
# 浏览器 http://localhost:9090/alerts
```

## 四、5 条核心告警规则

创建 `alert-rules.yaml`：

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: k8s-core-alerts
  namespace: monitoring
  labels:
    release: kube-prometheus
spec:
  groups:
  - name: kubernetes-core
    rules:
    - alert: PodPending
      expr: sum(kube_pod_status_phase{phase="Pending"}) > 0
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} Pending 超过 5 分钟"

    - alert: NodeNotReady
      expr: kube_node_status_condition{condition="Ready",status="true"} == 0
      for: 1m
      labels:
        severity: critical
      annotations:
        summary: "节点 {{ $labels.node }} 状态 NotReady"

    - alert: PodOOMKilled
      expr: kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} > 0
      for: 0m
      labels:
        severity: critical
      annotations:
        summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} 被 OOM Kill"

    - alert: HighCPUUsage
      expr: sum(rate(container_cpu_usage_seconds_total{container!=""}[5m])) by (pod, namespace) / sum(kube_pod_container_resource_limits{resource="cpu"}) by (pod, namespace) > 0.8
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} CPU 使用率 > 80%"

    - alert: HighMemoryUsage
      expr: sum(container_memory_working_set_bytes{container!=""}) by (pod, namespace) / sum(kube_pod_container_resource_limits{resource="memory"}) by (pod, namespace) > 0.8
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} 内存使用率 > 80%"
```

```bash
kubectl apply -f alert-rules.yaml
```

> ⚠️ 踩坑（OOMKilled 规则）：
> 1. 新版 kube-state-metrics 指标名从 `kube_pod_container_status_terminated_reason` 改成了 `kube_pod_container_status_last_terminated_reason`。
> 2. 该指标是 **gauge**（值恒为 0 或 1），不是 counter，所以 `increase(...[5m])` 永远算不出值。应直接写 `> 0` 判断。
> 3. OOMKilled 是瞬时事件，`for: 0m` 即时触发，不需要等窗口。

## 五、全链路验证：用故障触发告警

### 验证 1 · PodPending

```bash
kubectl run test-pending --image=nginx:alpine --requests=memory=1Ti
# 5 分钟后，http://localhost:9090/alerts 搜 PodPending，状态从 inactive → pending → firing
kubectl delete pod test-pending
```

### 验证 2 · NodeNotReady

```bash
docker ps | grep k8s-lab-worker2   # 找 worker 容器名
docker stop k8s-lab-worker2
# 等约 40 秒，NodeNotReady 变 firing
docker start k8s-lab-worker2
```

### 验证 3 · PodOOMKilled

```bash
kubectl apply -f oom-pod.yaml      # 见第一篇故障 3
# 立即触发，PodOOMKilled 变 firing
kubectl delete pod oom-killer --force --grace-period=0
```

### 验证 4 · Grafana 大盘对照

故障触发后，在 Grafana（localhost:3000）切到对应大盘，观察曲线变化：

| 仪表盘 | 观察什么 |
|--------|---------|
| Kubernetes / Compute Resources / Pod | OOMKilled 前后内存曲线 |
| Kubernetes / Compute Resources / Node | worker 宕机时 CPU 归零 |
| Kubernetes / Kubelet | 节点 NotReady 后心跳消失 |
| Kubernetes / API Server | API 请求延迟 |

## 六、全链路验证结论

验证闭环：**制造故障 → kube-state-metrics 指标异常 → Prometheus 告警 firing → Grafana 可视化**。每完成一轮，把告警状态截图保存，作为「自建 K8s 全链路可观测体系」的实物证据。

## 七、环境真实发现的问题（脚本巡检 + 人工排查）

| 问题 | 现象 | 根因 |
|------|------|------|
| grafana Readiness 失败 | connection refused | Grafana 内存 limit 200Mi 太小，被 OOM 循环重启 |
| metrics-server Liveness 失败 | context deadline exceeded | 未加 `--kubelet-insecure-tls` 参数 |
| kube-proxy FailedToUpdateEndpoint | Unauthorized | RBAC 权限问题 |

## 八、清理

```bash
# 不想用了直接卸载
helm uninstall kube-prometheus -n monitoring
```
