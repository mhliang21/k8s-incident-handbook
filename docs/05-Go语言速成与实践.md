# K8s 实战手册 · 第五篇：Go 语言速成与实践

> 环境：Go 1.26 · Windows
> 本篇记录 Go 语言速成的学习路径，以及两个实践工具——HTTP 并发探测服务（httpprobe）和单词统计 CLI（wordstats），重点练习 **goroutine（并发）**、**interface（接口）**、**error（错误处理）** 三个核心概念。配套仓库：<https://github.com/mhliang21/go-tools>。

## 一、为什么 K8s 方向要学 Go

K8s 本身是 Go 写的：kube-apiserver、kubelet、scheduler、etcd、client-go 全是 Go。这意味着：

- 用 kubectl 只能「操作」K8s，用 client-go 才能「读懂 / 改造 / 编写」K8s 生态代码；
- 面试时「熟悉 K8s」和「能用 Go 写控制器 / operator」是完全不同的量级；
- 前面四篇笔记（排查 / 监控 / 巡检 / CI/CD）都是在「用」K8s，这一篇开始「进入」K8s 的实现语言。

## 三、三个核心概念

| 概念 | 一句话理解 | 在两个工具里的落点 |
|------|-----------|-------------------|
| **goroutine** | 轻量级线程，`go func()` 一键并发 | `probeAll` 为每个目标起 goroutine 并发探测 |
| **interface** | 面向抽象编程，定义行为不定义类型 | `Prober`（HTTP/TCP）、`Formatter`（text/json）多态 |
| **error** | 错误是值，必须显式处理 | 超时/连接失败/未知格式/空输入，`%w` 包装错误链 |

## 四、工具一：httpprobe（HTTP 并发探测服务）

演示 **goroutine 处理并发请求 + 接口多态**。

### 核心设计

**1. Prober 接口（interface 多态）**

```go
type Prober interface {
    Name() string                 // 探测类型名
    Probe(ctx context.Context) Result  // 执行一次探测
}
```

`HTTPProber`（HTTP GET）和 `TCPProber`（TCP 连接）是两种完全不同的实现，但上层 `probeAll` 只依赖接口，不关心具体是哪种——这就是「面向抽象编程」。

**2. probeAll 并发探测（goroutine 核心）**

```go
func probeAll(ctx context.Context, probers []Prober) []Result {
    results := make(chan Result, len(probers))
    var wg sync.WaitGroup
    for _, p := range probers {
        wg.Add(1)
        go func(prober Prober) {   // 每个目标一个 goroutine
            defer wg.Done()
            results <- prober.Probe(ctx)
        }(p)                       // 参数传值，避免闭包捕获循环变量
    }
    go func() { wg.Wait(); close(results) }()
    // range channel 收集结果
}
```

**3. 两层并发**：`net/http` 为每个进来的请求自动起 goroutine（Go 处理并发请求的天然机制）；请求内部又用 `probeAll` 并发探测多个目标。

### 验证结果

```bash
curl "http://localhost:8080/probe?target=http://baidu.com&target=http://github.com"
# → 两个目标并发探测，latency 不叠加（559ms + 1.2s，而非串行的 ~1.8s）

curl "http://localhost:8080/probe?target=tcp://localhost:6379"
# → 连接拒绝，正确返回 {"status":"error","error":"...actively refused..."}，不 panic
```

## 五、工具二：wordstats（单词统计 CLI）

演示 **接口抽象 + 健壮错误处理**。

### 核心设计

**1. Formatter 接口 + 注册表（interface 多态）**

```go
type Formatter interface {
    Format(stats []WordCount) (string, error)
}

var formatters = map[string]Formatter{
    "text": TextFormatter{},
    "json": JSONFormatter{},
}
```

加新格式只需在注册表加一行，不改任何调用方代码。

**2. 健壮错误处理（error 惯用法）**

```go
func countWords(r io.Reader) ([]WordCount, error) {
    // ...
    if err := scanner.Err(); err != nil {
        return nil, fmt.Errorf("读取输入失败: %w", err)  // %w 保留错误链
    }
    if len(freq) == 0 {
        return nil, ErrEmptyInput  // 哨兵错误，调用方可 errors.Is 判断
    }
}
```

**3. 统一错误出口**：`run()` 返回 error，`main` 统一打印并 `os.Exit(1)`，不散落 `os.Exit`。

### 验证结果

| 场景 | 结果 |
|------|------|
| `-f main.go -format text` | 正确输出按次数降序的单词频率 |
| `-f main.go -format json` | 正确输出 JSON |
| `-f not-exist.txt` | `打开文件失败: ...` 退出码 1 |
| `-format xml` | `未知的输出格式 "xml"` 退出码 1 |
| 缺 `-f` 参数 | `缺少 -f 参数` 退出码 1 |

## 六、踩坑记录

**1. goroutine 闭包捕获循环变量**

经典陷阱：`go func() { ... p ... }()` 里直接引用循环变量 `p`，会导致所有 goroutine 读到同一个（最后的）值。修复：用参数传值 `go func(prober Prober){...}(p)`。

**2. 并发返回结果顺序不确定**

多个 goroutine 通过 channel 返回，顺序随机。需要稳定输出时必须排序（`sort.Slice` 按 target 排序）。

**3. `go run` 后台进程不回收**

本地用 `go run main.go &` 起的服务，回合结束后进程不回收，端口一直占用。修复：先 `go build` 编译出 exe 再运行，进程 PID 可直接 kill；或运行前用 `netstat -ano | grep :8080` 查占用、`taskkill /PID <pid> /F` 清理。

**4. `git push -u <带token的URL>` 会把 token 写进 .git/config**

用 PAT 推送时若 `-u` 传的是含 token 的 URL，git 会把带 token 的 URL 设为 branch 的 upstream，token 就持久化到了本地配置。修复：推送后 `git config branch.main.remote origin` 改回干净的 remote，并 grep 确认无 `ghp_` 残留。
